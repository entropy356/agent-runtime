# Demo 的组织与演化

**Demo 是围绕一个相对稳定的实验目标持续演化的实验单元，而不是某个固定版本的程序。**

一个 Demo 可以持续调整实现、替换算法、修复问题，并通过多轮实验逐步回答它所关注的问题。只要实验目标没有发生实质变化，这些调整就属于同一个 Demo 的演化。

## 在原 Demo 内持续演化

当实验目标保持不变时，直接修改原 Demo，包括：

- 函数调整、Bug 修复和代码重构；
- 算法优化或替换；
- 更换模型、Provider 或其他实现细节；
- 在同一实验目标下比较不同算法或参数。

不需要因为一次函数调整或算法版本变化就创建新的 Demo，也不需要在代码目录中长期保留每个历史版本。实现的变化由 Git 记录。

## 何时创建新的 Demo

当要验证的问题或实验目标发生实质变化时，创建新的 Demo。

例如：

- Demo 1：验证情绪如何影响记忆检索；
- 后续 Demo：验证情绪惯性如何影响状态演化；
- 后续 Demo：验证情绪如何影响 Runtime 运行频率。

新 Demo 是独立的实验单元，可以拥有自己的实现、依赖、运行方式、说明和测试。不同 Demo 可以暂时复制代码，不必为了复用而提前建立公共抽象；当多个 Demo 确实出现稳定的共同需求时，再考虑提取共享模块。

## 记录实验信息

Demo 文档应帮助读者理解实验，而不只是说明代码如何运行。

每个 Demo 的说明应围绕实际需要记录：

- **目标**：希望验证或探索什么；
- **方法**：当前实现如何进行实验；
- **观察与结论**：实验中发现了什么，哪些假设得到支持或被否定；
- **局限**：当前实验还不能说明什么；
- **运行方式**：如何复现当前实验。

函数级调整、普通重构和 Bug 修复通常只需要 Git 历史，不必逐项写成实验记录。只有当一次调整带来了有价值的观察、结论或设计变化时，才需要补充文档。较大的算法对比可以在 Demo 内增加独立实验记录。

失败实验和被否定的假设，只要能帮助后续理解问题，也值得保留。

## Git 与 Demo 文档的分工

- **Git** 保存实现如何变化，提供可追溯的原始历史。
- **Demo 文档** 说明实验为什么变化、观察到了什么，以及这些结果意味着什么。

不重复抄写提交时间线，也不要求每次代码变化都维护一份说明。目标是保留有价值的实验信息，同时避免历史维护成为负担。

## 命名

Demo 使用稳定编号和简短主题名，例如：

```text
demos/
├── demo1-emotion-memory/
├── demo2-emotion-inertia/
└── demo3-emotion-clock/
```

编号一经使用就保持稳定。Demo 的实现可以持续演化，目录名和编号不因内部函数或算法调整而改变。
