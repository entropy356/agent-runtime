# 项目愿景：信息化历史

项目不再把「最小化历史」作为目标，而是转向「信息化历史」。

历史不只是需要压缩或清理的冗余记录，也不应该只是按时间排列、很少再被利用的变更日志。它包含项目形成过程中的设计依据、实验结果、失败经验和决策脉络；这些信息能够帮助项目理解自身、指导后续工作。

## 核心原则

**不追求历史最少，而追求历史的信息密度和可利用性。**

- **Git 保存原始变化**：代码、文档和配置的完整变更由 Git 历史记录。
- **文档提炼项目知识**：当前设计记录项目现在如何理解问题；实验文档记录假设、方法、观察结果、结论与局限；必要时记录重要决策及其依据。
- **避免平行复制**：文档不重复抄写 Git 时间线，而是提炼仅靠提交记录难以直接看出的语义信息，并尽可能关联对应提交、实验或实现。
- **保留有价值的失败**：失败实验、被否定的假设和设计转向，只要能为后续工作提供信息，就值得被记录。
- **让历史可以被利用**：历史信息应当可检索、可关联，并能参与后续设计、实验和开发，而不只是被动保存。

## 历史如何进入项目

项目历史可以分为两个互补层次：

1. **原始历史**：由 Git 保存，提供可追溯的变更事实。
2. **提炼后的信息**：由设计文档、实验记录和决策说明承载，表达变化背后的原因、证据和结论。

例如，一个 Demo 不只记录代码，还应说明它想验证什么、观察到了什么、哪些结论成立、有哪些局限，以及它对当前设计意味着什么。

未来可以让 AI 协助从提交、实验和设计变更中提炼这些信息，但提炼结果应回到项目文档中，成为可检查、可修订、可追溯的项目知识。

## 与「最小化历史」的关系

这并不意味着保存所有过程、聊天记录或中间产物。低价值的重复信息仍然应该被省略；已经失去用途的临时材料也不必长期保留。

改变的是优化目标：

- 不是尽可能减少历史本身；
- 而是减少维护历史的负担，保留并组织真正有价值的信息；
- 让历史从存档转化为项目知识的一部分。

**历史不应该被简单地保存或删除，而应该被转化为信息，成为项目自身的一部分。**
