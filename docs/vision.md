# 项目愿景：信息化历史

信息化历史的目的是为项目演化积累**可比较的数据**。通过记录设计、实现和实验在不同阶段的状态与结果，让项目能够比较不同方案、检验过去的判断，并观察自身如何演化。

## 核心原则

**记录有比较价值的信息，而不是单纯积累历史叙述。**

- **保留可比较的实验数据**：记录实验目标、假设、变量、条件、方法、结果和结论，使不同实验之间能够对照。
- **保持记录口径一致**：对需要比较的指标、参数、单位和测试条件使用明确且稳定的定义；条件不同的结果应标明差异，避免把不可比的数据直接放在一起。
- **关联实现与结果**：实验记录应关联对应的代码版本、配置、模型、数据集或其他影响结果的条件，使结果可追溯、可复现。
- **保留失败与负面结果**：没有效果、效果变差或推翻原有假设的实验，同样是有比较价值的数据。
- **让结论有证据**：设计判断和方案选择尽可能关联实验结果，而不只保留最终结论。

## 比较什么

项目历史应支持不同尺度的比较：

- 同一实验中，不同函数、算法或参数的效果；
- 同一目标下，不同 Demo 或实现方案的效果；
- 同一方案在不同模型、数据或运行条件下的表现；
- 项目不同阶段的设计假设、实现状态与实验结果；
- 预期结果与实际结果之间的差异。

比较的目的不是简单排列优劣，而是帮助理解哪些因素造成了差异，以及结论适用于什么条件。

## 历史如何进入项目

项目中的信息由两个互补部分构成：

1. **原始变化**：Git 保存代码、文档和配置的版本及变更。
2. **比较记录**：项目文档或结构化实验数据记录变化的目的、条件、结果和解释，并关联对应的 Git 版本。

一次有比较价值的实验，至少应尽可能说明：

- **目标与假设**：要回答什么问题，预期是什么；
- **变量与条件**：改变了什么，哪些条件保持一致；
- **方法**：如何执行实验；
- **结果**：观察值、指标或具体现象；
- **结论与局限**：结果支持或否定了什么，结论适用于哪些条件；
- **实现关联**：对应的代码版本和配置。

不要求每次函数调整都生成一份实验报告。普通修复和重构由 Git 记录；只有当变化产生了值得比较的结果或影响了设计判断时，才需要形成比较记录。

## 信息的组织与利用

记录应当可检索、可关联，并尽可能采用便于后续处理和比较的结构。对于需要长期比较的实验，应优先保留原始结果、关键配置和明确的指标定义，而不只保留自然语言总结。

未来可以让 AI 协助从 Git 变更、实验运行和设计讨论中提取比较信息，整理差异、发现趋势并帮助检验假设。提取结果应能回溯到原始代码版本和实验依据。

信息化历史不意味着保存所有聊天记录、中间产物或重复叙述。应保留的是能够支持比较、复现、解释和后续决策的信息。

**让项目的每次重要变化都留下可比较的依据，使项目能够用自己的历史检验自己的判断。**
